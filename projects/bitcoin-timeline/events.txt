# Format:
# block height | category | title | technical description and references
# Lines starting with # are ignored.
#
# Block height is the sole chronological ordering key.
# One event per line; continuation lines may be indented if a parser supports them.
# Heights for dated software/governance/ecosystem events provide ordering; descriptions focus on the event itself.
# Pretty references are extracted automatically from the description.
#
# Taxonomy:
# consensus             = canonical-mainnet block/transaction validity rule that changes which blocks or transactions are valid.
# consensus-maintenance = consensus implementation change that restores intended validity or changes historical/deployment handling without activating a new forward-chain rule at that height.
# activation            = signaling, lock-in, deployment state, or activation coordination that does not itself define a canonical validity rule.
# policy                = relay, mempool, wallet-broadcast, or default mining-template standardness; policy does not change block validity.
# fork-choice           = rule used to select the canonical branch among otherwise valid competing chains.
# security              = vulnerability, disclosure, or security fix; a separate consensus event is used when the fix changes or restores validity behavior.
# incident              = actual exploit, accidental chain split, invalid mining, DoS demonstration, or operational failure.
# fork                  = deliberate/minority/alternative incompatible rule set or planned chain split that is not canonical Bitcoin consensus.
# release               = publicly distributed stable Bitcoin / Bitcoin-Qt / Bitcoin Core release or public platform hotfix.
# chain                 = mining, difficulty, subsidy, issuance, natural reorg/stale-race, or block-level milestone without a validity-rule change.
# transaction           = technically, economically, historically, or structurally notable transaction/on-chain data event.
# governance            = BIP process, stewardship, agreements, upgrade debate, and coordination history.
# development           = protocol/specification/software-history/test-network milestone that is not itself a canonical-mainnet validity change.
# ecosystem             = adoption, infrastructure, and higher-layer protocol milestone.
# market                = price discovery, exchange-rate milestones, trading-market milestones, and historically important Bitcoin-denominated financial-market events.
# culture               = culturally notable Bitcoin event, meme, or on-chain tribute.
#
# Invariants:
# - Every identified canonical-mainnet validity-rule change has a standalone `consensus` event.
# - Historical/deployment-only consensus-code changes use `consensus-maintenance`.
# - Policy and fork-choice changes are never labeled consensus merely because they influence network behavior.
# - Vulnerabilities/incidents and the consensus rules that fix them are separate cards when both are historically meaningful.
# - Multi-BIP deployments receive separate consensus cards when the BIPs define materially distinct validity semantics.
# - Release cards summarize software; consensus, policy, security, and activation milestones are not hidden inside release descriptions.
# - Deliberate/minority alternative rules are `fork`; accidental invalid/stale/network failures are `incident` or `chain` as appropriate.
#
# Coverage:
# Bitcoin protocol/consensus and fork-choice history; major activation/fork/governance episodes; consensus-critical and major Bitcoin Core security events;
# public reference-client releases; selected high-impact relay/mining-policy transitions; significant natural reorgs and invalid mined blocks;
# major development-network/ecosystem milestones; and curated unusual or technically instructive transactions.
# major market-price milestones, socially significant Bitcoin events, and curated historically notable blocks/transactions;
# This is deliberately curated rather than an exhaustive list of every BIP, CVE, stale block, release candidate, or policy-default tuning.
#
# Source hierarchy:
# Prefer BIPs, Bitcoin Core/bitcoin.org releases and advisories, source history, contemporaneous developer/forum/mailing-list material, and block data.
# Strong secondary sources are used only where primary material is incomplete or impractical to reconstruct.
